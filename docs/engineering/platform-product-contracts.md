## 1. Purpose

Define versioned, product-neutral contracts between ExITS Platform and products (HealthCare, PinoyBusinessPOS, future products) so later databases, APIs, events, projections, and authorization can be implemented without ambiguous ownership, synchronous Platform coupling on every transaction, or leakage of sensitive product payloads.

This document is **policy and shape only**. No C# types, JSON schemas, tables, or message brokers are defined here.

## 2. Contract principles

1. Platform is system of record for identity, organizations, memberships, catalog, plans, subscriptions, SaaS payments, and entitlements (ADR-011).
2. Products own operational data and operational permissions.
3. Cross-boundary references use **stable IDs only** — no cross-database foreign keys.
4. Products use **local projections**; normal operations do not synchronously query Platform per transaction.
5. Contracts are **versioned and additive** by default; breaking changes need a new major version.
6. Consumers assume **at-least-once** delivery and must be **idempotent**.
7. Clinical-sensitive and POS operational detail **never** enter Platform commercial contracts.
8. SaaSPayment ≠ RetailPayment ≠ CreditPayment.
9. Patient ≠ Platform User; POS Customer ≠ Platform User.
10. Transport selection (HTTP poll, message bus, etc.) is **deferred** (OD-03).

## 4. Identity projection

### Allowed projected fields (minimum)

| Field | Purpose |
|---|---|
| PlatformUserId | Stable reference |
| DisplayName | UI / historical readability |
| NormalizedEmail | Where product needs contact matching (minimize) |
| AccountStatus | Active / Suspended / Deactivated |
| OrganizationMembershipStatus | For linked org |
| ProductAccessStatus | May use this product |
| IdentityVersion | Projection concurrency |
| EffectiveAt | When facts became true |
| LastSynchronizedAt | Product clock |

### Must not replicate

Password hashes, refresh-token hashes, MFA secrets, password-reset tokens, full login history, security configuration unused by the product, unnecessary PII.

### Rules

- Product profile/employee/patient/customer data remains **product-owned**.
- Platform User suspension must eventually invalidate product access (via event/projection).
- Historical operational records **retain** actor PlatformUserId (and optional display-name snapshot) after disable/delete.
- Display-name snapshots may be retained for readability; **PlatformUserId remains authoritative**.

## 8. Entitlement contract

### Authoritative + projection fields (minimum)

### Feature value types (typed; avoid free-form bags)

| Type | Use |
|---|---|
| Boolean | Feature on/off |

| QuantityLimit | Quotas with unit |

## 9. Trial-expiration behavior

Approved **three-month Utang trial** ([subscriptions-and-billing.md](../product/subscriptions-and-billing.md)):

### Allowed after expiry

- View existing customers, balances, historical credit entries, payment history
- Receive partial/full payment against **existing** debt via **Cash** or **GCash** (manual GCash; reference required)
- Export/access data where separately approved
- Upgrade or renew subscription

### Blocked after expiry

- Create new customer credit / increase debt / add new credit entries
- Use features not allowed by expired entitlement

POS retail payment method codes and Cash/GCash field rules: [pinoy-business-pos-requirements.md](../product/pinoy-business-pos-requirements.md).

### Open (do not guess)

| Question | Status |
|---|---|
| Create new cash-only customer after trial expiry? | **Open** — OD-07 |
| Edit customer contact info after expiry? | **Open** — OD-08 |
| Correct erroneous historical entry (elevated + audit)? | **Open** — OD-09 (direction: elevated + audit preferred; finalize in Phase 6) |
| Offline device with stale entitlement after expiry? | Bound by projection states + Phase 7; stale window duration **not** fixed here (R-022) |
| Duplicate GCash reference hard-block vs warn-only? | **Open** — OD-11 (warn minimum is approved) |

Conceptual envelope (transport-agnostic):

| Field | Rule |
|---|---|
| EventId | Immutable UUID |
| EventType | Stable name |
| EventVersion / SchemaVersion | Versioning |
| OccurredAt / PublishedAt | **UTC only** |
| CorrelationId / CausationId | Tracing |

| Payload | Contracted fields only |

Assumptions: at-least-once delivery; duplicate and out-of-order tolerance; additive evolution; unknown-field tolerance for minor versions; reject/quarantine unsupported **major** versions; **no secrets or clinical payloads**.

Message broker **not** selected in this WP.

## 11. Versioning

| Version kind | Changes when |
|---|---|
| EventVersion | Event type payload shape for that type |
| SchemaVersion | Shared schema family (e.g. entitlement schema) |
| AggregateVersion | Per-aggregate causal order |
| EntitlementVersion | New authoritative entitlement snapshot for org+product |
| ProjectionVersion | Local applied commercial projection revision |
| API version | Later HTTP surfaces (deferred) |

Rules: prefer additive changes; do not silently repurpose fields; do not add required fields to an existing version without compatibility; enum expansion must be tolerated safely; breaking → new major; products declare supported versions; Platform keeps support through approved migration window; historical events remain interpretable. **Do not** tie contract versions to assembly versions.

## 12. Idempotency and ordering

Requirements:

- Deduplicate by EventId (and optionally business idempotency keys).
- Prefer AggregateVersion / EntitlementVersion checks before apply.
- Tolerate replays, delayed and out-of-order events, duplicate payment confirmation and entitlement updates.
- Concurrent updates: last authoritative version wins after validation; never apply older over newer without reconciliation.
- Manual reconciliation when checksum/version/schema disagreement cannot be auto-resolved.

Projection metadata (conceptual, not tables): last applied version, last event id, last synchronized time, current schema version, reconciliation-required flag.

## 13. Projection states

See [entitlement-state-matrix.md](entitlement-state-matrix.md). Summary:

| State | High-level behavior |
|---|---|
| Current | Use normally |
| Refresh due | Use; schedule refresh |
| Temporarily stale | Allow approved ops for **bounded** interval (duration TBD — R-022) |
| Grace period | Per grace entitlements |
| Suspended | Block entitlement-protected writes |
| Expired | Trial/subscription expired rules |
| Invalid | Fail closed for protected features |
| Unsupported version | Fail safe; alert; grant no unknown features |
| Reconciliation required | Restrict risky writes; request snapshot |
| Never initialized | Do **not** grant paid features by default |

**Fail-closed** (default): financially sensitive, privacy-sensitive, administrative. **Fail-open** only for explicitly approved read-only continuity (e.g. viewing existing balances during temporary Platform outage while projection still within stale policy).

## 14. Reconciliation

Triggers: missing events, out-of-order versions, checksum mismatch, unsupported schema, subscription disagreement, bad override expiry, missing org mapping, duplicate ids.

Future reconciliation operation may: request authoritative snapshot; compare versions; **replace commercial projection only**; preserve product operational data; audit reason/actor; never cascade-edit operational domain via Platform.

APIs not implemented in this WP.

## 15. SaaS payment contract

Fields (minimum): SaaSPaymentId, PlatformOrganizationId, ProductCode, SubscriptionId, Amount, Currency, PaymentMethod, ExternalReference, SubmittedAt, VerificationStatus, VerifiedAt, VerifiedByPlatformUserId, RejectionReason, EffectiveSubscriptionAction, Version, audit correlation.

```text
SaaSPayment     → org pays ExITS for software
RetailPayment   → retail customer pays store for goods (methods: cash, gcash, customer-credit)
CreditPayment   → payment against POS customer credit (methods: cash, gcash)
```

Separate bounded contexts, entities, permissions, and audit trails.

Platform may later accept **GCash as a SaaS** payment method for subscription billing. That is **not** the same as POS retail GCash and must not reuse POS payment entities.

```text
Platform GCash → business pays ExITS
POS GCash      → retail customer pays the store
```

POS MVP GCash is **manually verified** by cashier/authorized user (no API/webhooks/QR automation in first MVP). See [pinoy-business-pos-requirements.md](../product/pinoy-business-pos-requirements.md).

## 16. Audit correlation

Cross-boundary fields allowed: CorrelationId, EventId/RequestId, PlatformUserId, PlatformOrganizationId, ProductCode, product-local actor ID, resource type/id, action code, result, OccurredAt (UTC), DeviceId (later), client app id, support reason.

**Do not send:** medical-note content, diagnoses, clinical payloads, credit remarks, sale line items, inventory details, secrets, tokens. Platform may record that an action occurred without product-sensitive content.

## 17. Deletion and retention

| Action | Meaning |
|---|---|
| Account deactivation | Platform user cannot authenticate; historical refs remain |
| Membership removal | Lose org/product access; product may retain local profile history |
| Product-access removal | Coarse product gate closed |
| Subscription cancellation / org suspension | Commercial state; product enforces via projection |
| User deletion request | Platform workflow; products receive unlink/anonymize contracts — **no DB cascade** |
| Product-local profile deletion | Product owns |
| Operational retention | Product owns for domain records |
| Anonymization | Product/Platform per data class |
| Legal hold | Later / compliance |

Historical audit and financial records may require retention. Stable actor IDs remain interpretable after deactivation. **Legal retention periods pending compliance review (OD-10).** Platform must not cascade-delete product operational rows through database relationships.

## 18. Security and privacy

Classifications: Public metadata, Internal operational metadata, Personal data, Security-sensitive, Financial, Clinical-sensitive, Product-confidential — see [data-classification-matrix.md](data-classification-matrix.md).

Minimum-sharing: only required fields; no clinical in Platform commercial contracts; product audit details stay local; no tokens/secrets in contracts; redact sensitive logs; support tooling must not expose unrestricted product data. Not a full legal framework.

## 19. API / event / projection decision rules

| Style | Use when |
|---|---|
| **Synchronous Platform API** | Login/token; admin commands; payment submit; membership verify without trusted local session; reconciliation request; admin query needing live authority |
| **Asynchronous event** | Subscription/entitlement/org/membership/user-suspension/product-activation/payment-confirmation effects |
| **Product-local projection** | Normal feature enforcement, authz context, startup, offline-tolerant ops |
| **Manual reconciliation** | Missing events, unsupported versions, mapping failures, admin repair |

Transport protocols deferred (OD-03).

## 21. Explicitly prohibited data

In Platform↔product commercial/identity contracts and Platform audit payloads:

- Password/MFA/reset/refresh material
- Medical notes, diagnoses, clinical documents
- Patient clinical identifiers beyond optional PlatformUserId linkage on product side only
- POS credit remarks, sale lines, inventory balances, supplier commercials
- Secrets, private keys, raw payment card data
- Cross-product operational dumps
- Shared EF entities / DbContext assumptions
